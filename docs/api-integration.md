# API integration status

The pinned Swagger snapshot has **128 REST paths, 146 operations and 312 schemas**. `npm run generate:api` creates `src/api/generated/openapi.ts` for every REST operation. `npm run check:api` fails if a path or method is missing from that generated file.

| Area                                                                                                                                 | Generated contract                       | Connected to a real screen             |
| ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- | -------------------------------------- |
| Auth login and logout                                                                                                                | Yes                                      | Yes                                    |
| Auth refresh (`POST /auth/refresh`)                                                                                                | Yes                                      | Yes, automatic (see below)             |
| Auth change password                                                                                                     | Yes                                      | No                                     |
| Admin APIs                                                                                                                           | Yes, because they are in Swagger         | No; the frontend does not invoke them  |
| Question proposals and lecturer review (`/sessions/*`, `PUT /questions/{id}`, `GET /subjects`)                                       | Yes                                      | Yes, in signed-in sessions (see below) |
| Practice by question set, answer, rate / report error, AI refine (`/users/{id}/sessions`, `/sessions/{id}/questions`, `/questions/{id}/answer|rate|ai-refine|ai-apply`) | Yes | Yes, in signed-in sessions (see below) |
| Games (`/games/*`, review-error, `/badges/me`): check-in, Game 1/2/4/6 predictions, history, leaderboard, Game 5 lecturer review | Yes | Yes, in signed-in sessions; admin rebuild/finalize have no UI (no Admin role) |
| Social, question bank, exams, relations, chat, notifications, search, media, devices, cosmetics and other REST groups        | Yes                                      | No; current screens remain demo driven |
| STOMP chat destinations                                                                                                              | Listed in `src/api/realtime-contract.ts` | No                                     |

Access tokens live 15 minutes. For `platform: WEB` the backend returns `refresh_token: null` in JSON and sets the 7-day refresh token as an HttpOnly cookie `refreshToken` (`Path=/api/v1/auth`, `Secure`, `SameSite=Strict`). `src/api/client.ts` refreshes ~1 minute before `exp` and, on a 401 / code 9998, refreshes once (shared by concurrent requests) and replays the original request. `POST /auth/refresh` must be sent with **no body**: an empty JSON body makes the backend ignore the cookie. Because the cookie is `Secure` and `SameSite=Strict`, open the dev server as `http://localhost` (not a LAN IP) and keep the API same-origin (Vite proxy or same host).

In API sessions the feed merges `GET /activity-feeds` (friends and followed users only), `GET /posts/me` and the 30 newest public posts of everyone from `GET /search?type=POST` with an empty query. Search results are used only for ids; each post is loaded with `GET /posts/{id}` for live counts and the backend privacy check, and posts the viewer may not see are dropped. Ordering stays: own and friends' posts first, then newest.

The STOMP destinations and DTO names are written in OpenAPI `info.description`, not as machine-readable operations or component schemas. The documented publish fields are represented in `realtime-contract.ts`; broadcast payloads remain `unknown` until the backend publishes schemas. This avoids inventing fields and does not imply a working WebSocket connection.

Proposal and review screens go through `src/features/proposals/proposalGateway.ts`. A signed-in (API) session calls only the REST endpoints and shows backend errors as they are; it never falls back to demo data or reports a failed action as successful. A demo session uses only `src/features/proposals/demoStore.ts`, one store shared by the student and lecturer screens, so a demo proposal reaches the lecturer queue and approved questions appear in the student bank. Swagger has no endpoint for resolved-session history or for listing bank questions, so in API sessions the history tab only keeps sessions completed while it is open, and the lecturer exam bank cannot be listed. The student `/bank` page is a different thing: a shared pool of question sets students posted (approved or not), for peer practice, rating and comments. In API sessions it reads `GET /search?type=SESSION` with an empty query (returns every set; in testing it returned only RESOLVED sets) through `src/features/bank/bankGateway.ts`, never shows the session status, and opens `PracticeSessionModal`, which also lists and posts per-question comments (`/comments`, `target_type=QUESTION`). `src/api/exams.ts` (exam generation, exam list/detail/export, question-bank export, subjects, lecturer course classes and class students) follows the same rule: API sessions call only REST, empty responses stay empty and errors are thrown to the screen; mock exam data is used only in demo sessions.

Business rules kept by the UI: `POST /sessions/approve` is the lecturer choosing questions into the subject's exam bank (APPROVED questions of a subject; shared by its lecturers). Lecturers can collect questions from several students' sets in a basket and approve them in one call. Students never see which of their questions were chosen: student screens show only the set status, practice shows every question of a resolved set, and the question source (AI or human) is not displayed. `practiceGateway.ts` serves profile question sets and practice; AI refine uses `ai-refine` then `ai-apply`. Swagger has no JSON listing of the exam bank, so in API sessions the lecturer bank page links to automatic exam generation and bank export instead of listing questions.

Games follow Swagger, not older written specs: Game 3 has no endpoint (it is the author confidence sent when proposing questions), there is no Minigame 3 popularity game, and lecturers do not resolve games manually. Lecturers only review Game 5 error reports; Swagger has no endpoint listing all reports, so in API sessions the lecturer looks reports up by question ID (`GET /questions/{id}/ratings`, filtered by `is_error`). The review body uses the Swagger field name `is_comfirmed` as spelled.

`src/features/demo/components/modals/ApiReferenceModal.tsx` is an older UI demo map. It is not an API contract or a list of completed integrations.

The social Feed/Profile create, edit, delete, comment, reply, media preview and friend-first ordering are local demo interactions. They do not call the post, comment, friendship or activity-feed endpoints. The current `GET /activity-feeds` contract exposes cursor pagination but no friend-first sorting option; that ordering needs backend support before it can be guaranteed across all pages of real data.

Demo chat conversations are visible only to their listed participants, and demo messages are shared between those participants. Demo chat and feed changes synchronize between open same-origin browser tabs with `BroadcastChannel`; they are not persisted by a server and do not synchronize across devices. API chat and feed screens are still not connected. The documented STOMP chat destinations alone do not provide a working connection, and the current contract does not define a feed push destination.

The Push tab in Settings currently stores the six notification preferences in browser `localStorage` and an optional voice recording in IndexedDB. This is local-only configuration: it does not register a push subscription, send or receive system notifications, or synchronize settings between browsers/devices. Real push delivery, per-event server preferences, and delivery of a user's voice recording require backend API support.

When a feature is connected, use the typed `api` client with its exact Swagger path and method, handle the `code/message/data` envelope through `expectEnvelope`, then update this table. Multipart endpoints require the `multipartBody` serializer. Export endpoints currently return a download URL in a JSON envelope rather than a binary response.
